## D-001 分页插件未注册，列表接口分页完全失效

- **严重程度**：严重（数据正确性 + 性能）
- **优先级**：高
- **模块**：学生管理 / 分页查询
- **环境**：本地 8080，库 student_web（student 表 12 条数据）

**复现步骤**

1. 用管理员登录，取 token；
2. 请求 `GET /api/admin/students?page=1&size=10`；
3. 依次把 page 改为 2、9999，size 改为 0。

**实际结果**

| 请求 | size 回显 | current 回显 | total | pages | 实际返回条数 |
|---|---|---|---|---|---|
| `?page=1&size=10` | 10 | 1 | **0** | **0** | **12（全表）** |
| `?page=2&size=10` | 10 | 2 | 0 | 0 | 12（全表） |
| `?page=9999&size=10` | 10 | 9999 | 0 | 0 | 12（全表） |
| `?page=1&size=0` | 0 | 1 | 0 | 0 | 12（全表） |

数据库实际 12 条，接口无论传什么分页参数都返回全部 12 条，且 `total`、`pages` 恒为 0。

**预期结果**

`size=10` 时最多返回 10 条；`total` 等于数据库真实总数（12）；`pages` 等于 2；`page=9999` 返回空列表。

**根因分析（后端）**

`config/MybatisPlusConfig.java` 是一个空的 `@Configuration` 类，没有注册 `PaginationInnerInterceptor`：

```java
@Configuration
public class MybatisPlusConfig {
}
```

MyBatis-Plus 3.4+ 之后，`selectPage()` 的分页与 COUNT 依赖该拦截器。缺失时 SQL 不会拼接 `LIMIT`，也不会执行 COUNT，因此：
- `records` 返回全表；
- `Page.total` 保持默认值 0，`pages` 为 0。

**影响**

- 前端分页组件显示"共 0 条"、翻页无效；
- 数据量一旦上千，列表接口会一次拉全表，接口响应时间和内存占用随数据量线性恶化，属于潜在性能事故。

**修复建议**

```java
@Configuration
public class MybatisPlusConfig {

    @Bean
    public MybatisPlusInterceptor mybatisPlusInterceptor() {
        MybatisPlusInterceptor interceptor = new MybatisPlusInterceptor();
        interceptor.addInnerInterceptor(new PaginationInnerInterceptor(DbType.MYSQL));
        return interceptor;
    }
}
```

**回归用例**：`test_pagination.py::test_size_applied`、`test_total_is_real`、`test_page_out_of_range`（修复后由 xfail 变为 XPASS，应删除 xfail 标记）

## D-002 有成绩的学生无法删除，返回 500 系统异常

- **严重程度**：严重（核心功能不可用）
- **优先级**：高
- **模块**：学生管理 / 删除
- **环境**：本地 8080，库 student_web

**复现步骤**

1. 管理员新增学生 `TDEBUG02`；
2. 教师为该学生录入一条成绩（`POST /api/teacher/scores`，cid=C001，term=2025-2026-1）；
3. 管理员调用 `DELETE /api/admin/students/TDEBUG02`。

**实际结果**

```
HTTP 200
{"code":500,"message":"系统异常，请稍后重试","data":null}
```

再次查询，该学生仍在库中，删除未生效。

**预期结果**

删除成功，并级联清理该学生的成绩记录（或明确提示"该学生存在成绩记录，请先清理成绩"）。

**根因分析（后端）**

`score` 表存在外键 `fk_score_student (sid) REFERENCES student(sid)`，且未配置级联删除。`StudentController.deleteStudent()` 直接调用 `studentMapper.deleteById(sid)`，触发 `DataIntegrityViolationException`，被 `GlobalExceptionHandler` 的兜底分支捕获，统一返回 500"系统异常"。

**影响**

管理员无法删除任何一个已录入成绩的学生，业务上等于"删除功能对老数据失效"；错误提示是"系统异常"，用户与客服都无从判断原因。

**修复建议**

外键改为 `ON DELETE CASCADE`，或在 `deleteStudent()` 中先删 `score` 再删 `student`（同一事务内），并对该场景返回可读的业务提示。

**回归用例**：`test_student_crud.py::test_delete_student_with_score`

## D-003 业务校验失败返回业务码 500，错误码语义混乱

- **严重程度**：一般（接口规范 / 前端联调）
- **优先级**：中
- **模块**：全局
- **环境**：本地 8080

**复现步骤**

新增一个已存在的学号：`POST /api/admin/students`，body 中 sid 与库中已有学号相同。

**实际结果**

```json
{"code":500,"message":"学号已存在","data":null}
```

**预期结果**

业务码 400（或 409 Conflict），与"系统异常"区分开。

**根因分析（后端）**

`common/Result.java` 提供了两个重载：

```java
public static <T> Result<T> error(String message) { return new Result<>(500, message, null); }  // 默认 500
public static <T> Result<T> error(int code, String message) { ... }
```

`StudentController`、`ScoreController` 中的业务校验（`Result.error("学号已存在")`、`Result.error("删除失败")`、`Result.error("保存失败")`）都走了单参重载，业务码被固定成 500，与真正的系统异常无法区分。

**影响**

前端无法通过 code 区分"业务提示"和"系统故障"，只能靠 message 文案判断，国际化或文案调整后逻辑即失效。

**修复建议**

单参重载的默认码改为 400；或统一改用 `error(400, msg)`。

**回归用例**：`test_student_crud.py::test_add_duplicate`

## D-004 参数类型错误返回 500，未做参数校验

- **严重程度**：一般
- **优先级**：中
- **模块**：学生管理 / 分页查询

**复现步骤**：`GET /api/admin/students?page=abc&size=10`

**实际结果**：`{"code":500,"message":"系统异常，请稍后重试"}`

**预期结果**：`{"code":400,"message":"参数 page 格式错误"}`

**根因分析（后端）**：`page` 声明为 `Integer`，Spring 在做类型转换时抛 `MethodArgumentTypeMismatchException`，`GlobalExceptionHandler` 未单独处理该异常，落到 `Exception` 兜底分支，被当成系统异常。

**影响**：前端传参异常时用户只看到"系统异常，请稍后重试"，无法自助修正；监控上也会与真实故障混淆。

**修复建议**：在 `GlobalExceptionHandler` 增加 `MethodArgumentTypeMismatchException` 的处理，返回 400 + 具体参数名。

**回归用例**：`test_pagination.py::test_page_not_number`

## D-005 成绩分数未校验 0-100 区间，越界值可直接入库

- **严重程度**：严重（数据正确性）
- **优先级**：高
- **模块**：成绩录入
- **环境**：本地 8080，教师账号 T001

**复现步骤**

```
POST /api/teacher/scores
{"sid":"<测试学生>","cid":"C001","term":"2025-2026-2","usual":120,"finalScore":-10}
```

**实际结果**：保存成功，总分被计算为 `round(120*0.4 + (-10)*0.6) = 42`，脏数据直接入库。

**预期结果**：拒绝保存，返回"分数必须在 0-100 之间"。

**根因分析（后端）**：`ScoreService.saveOrUpdateScore()` 只校验了字段是否为 null（学号/课程/学期/平时分/期末分），没有校验数值区间；实体上也没有加 `@Min/@Max` + `@Valid`。

**影响**：成绩是系统的核心数据，越界值会让班级平均分、及格率、分数段分布全部失真，且前端表单校验可被绕过（直接调接口）。

**修复建议**

```java
@Min(0) @Max(100) private Integer usual;
@Min(0) @Max(100) private Integer finalScore;
```

Controller 方法加 `@Valid`，并在 Service 内做二次校验（防止内部调用绕过）。

**回归用例**：`test_score.py::test_score_out_of_range`

**修复过程中额外发现的一个坑（值得记一笔）**

MyBatis-Plus 3.5.9 起把分页插件依赖的 JSqlParser 拆成了独立模块，`PaginationInnerInterceptor` 不再随 `mybatis-plus-extension` 提供。只加配置类会编译报"找不到符号"，必须同时引入：

```xml
<dependency>
    <groupId>com.baomidou</groupId>
    <artifactId>mybatis-plus-jsqlparser</artifactId>
    <version>3.5.9</version>
</dependency>
```

版本必须与 starter 主版本一致，否则会出现类冲突。

**验证方式**

```
TEST_ENV=verify pytest -q     # 指向运行修复后代码的实例
38 passed
```
